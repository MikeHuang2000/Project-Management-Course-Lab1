## 1 变更描述与验收口径

来源：`00-customer-brief.md` §6——设备不可用时学生可登记候补，管理员可看候补名单；**候补通知、自动递补明确不在本次范围**。

| 决策点 | 建议 | 理由 |
|---|---|---|
| 登记触发条件 | **任意时段均可登记**，不强制要求"该时段不可用"；若该时段当前可借，只在输出里带 `available_now:true` 提示，不拒绝 | ①与 `05-architecture.md` §3.6"只在 approve 判冲突、submit 不判"保持单一口径；②可用性是随时间变化的（他人取消/归还），提交时强判"不可用"会出现"先查可用、登记却被拒"，迫使学生在两条命令间反复重试；③强判要多一条退出码 1 分支与一个"不可用"判定复用点，测试面变大而客户价值不变 |
| 去重规则 | 同一 `user_id` + 同一 `device_id` + 时段重叠（半开区间，公式同 §3.2）只允许 1 条 `waiting`；重复提交 → 退出码 1，`error=duplicate_waitlist` | 与 requests 的"同人同设备只 1 条 pending"（§2 应用层约束）口径对齐；**区间重叠无法用 UNIQUE 表达**，只能应用层判，库层再加一条"三段完全相同"的部分唯一索引作兜底 |
| 可见范围 | student 仅本人；admin 全部（需 `--all`）；director 退出码 3 | 沿用 §5 对 `request list/show` 的处理，主任只读统计，不扩权 |
| 与 CRQ-05 关系 | **候补不占用时段。** `waitlists` 不进 `CONFLICT_SQL`（现行 SQL 只读 `approved` requests 与未归还 loans），approve 判定一行不改 | 候补是"排队意愿"，不是"已批准占用"。若让候补占位，等于把未批准的申请当占用，与 §3.4"pending 不占用"直接矛盾，会破坏 CRQ-05 的唯一口径（R1 风险复活） |
| 编号 | **不重编号**：沿用客户原始编号 CRQ-10 作为"候补登记"，批准后由"变更候选"转"基线" | CRQ-10 已被 brief §3、`04-scope.md` §2/§6、`06-wbs.md` §3 三处引用，另起 CRQ-11 会留下悬空引用；仅在采纳方案 A 时新增 **CRQ-11 = 取消候补** |

验收口径（写入 RTM 时照抄，可测）：

| AC | 判定 | 对应 TC |
|---|---|---|
| AC1 | `waitlist join` 成功：退出码 0，库中 1 条 `waiting`，审计 `waitlist_join` 1 条 | TC-CRQ-10-01 |
| AC2 | 同人同设备重叠时段重复登记：退出码 1，库无新增 | TC-CRQ-10-02 |
| AC3 | 候补不占位：同一 pending 申请在"有 waiting 记录"与"无 waiting 记录"两个库上 approve，退出码与 `conflicts` 列表完全一致 | TC-CRQ-10-03 |
| AC4 | 名单可见性：admin 见全部、student 见本人、director 退出码 3 | TC-CRQ-10-04 |
| AC5（仅方案 A） | 取消本人 `waiting` → `cancelled`；他人或已取消 → 退出码 1 | TC-CRQ-11-01 |

## 2 影响面

### 2.1 数据模型（新增 1 张表）

**waitlists**（DDL 要点，不替代完整建表脚本）：

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | PK AUTOINCREMENT | |
| device_id | INTEGER | NOT NULL REFERENCES devices(id) | |
| user_id | INTEGER | NOT NULL REFERENCES users(id) | |
| start_at / end_at | TEXT | NOT NULL；应用层 `end_at > start_at` | ISO 8601 UTC，半开区间（NFR-07） |
| status | TEXT | NOT NULL CHECK IN ('waiting','cancelled') DEFAULT 'waiting' | 只有两态；`cancelled` 仅方案 A 可写入 |
| note | TEXT | 可空 | 用途备注，长度应用层限 200 字符 |
| created_at | TEXT | NOT NULL | |

- 索引：`(device_id, start_at, end_at)` 供名单过滤；`(user_id)` 供"我的候补"。
- 部分唯一索引兜底：`UNIQUE (user_id, device_id, start_at, end_at) WHERE status='waiting'`（只挡完全相同的三段重复，不替代 AC2 的重叠判定）。
- 不建 `notified_at`、`position`、`promoted_request_id`：通知与自动递补不在范围，提前建列等于给二期承诺。
- 现有四张表（users / devices / requests / loans）**结构与约束均不改**，故 §2 现有 DDL 仅追加、不重写。

### 2.2 CLI（新增 2–3 条命令，既有 16 条不动）

| 命令 | 参数 | stdout 要点 | 退出码 |
|---|---|---|---|
| `waitlist join` | `--device`、`--from`、`--to` 必填，`--note` 可选 | `{"waitlist_id":..,"status":"waiting","available_now":bool}` | 0, 1, 2, 3 |
| `waitlist list` | `--all`（仅 admin）、`--device`、`--status` 可选 | `{"items":[{"waitlist_id","device_id","user_id","start_at","end_at","status","created_at"}]}` | 0, 2, 3 |
| `waitlist cancel`（**仅方案 A**） | `--waitlist-id` 必填 | `{"waitlist_id":..,"status":"cancelled"}` | 0, 1, 2, 3 |

- 退出码沿用 §4 全局 5 档，**不扩增**（不用 4，4 仍专属 `request approve`）。
- 对既有命令的影响：①`init-db` 建表多一张，输出 JSON 不变；②`main.py` 只新增子命令组与分发，不改任何既有参数名/字段名；③**`seed` 不新增候补字段**——演示用的候补数据由演示脚本现场 `waitlist join` 生成，避免改 `seed` 的输出契约与 `TC-NFR-05-01` 的断言。
- 文件落点（`05-architecture.md` §1 的追加）：新建 `src/waitlist.py`（登记/去重/列表/取消），`main.py` 加子命令；**不改 `requests.py`**，approve 路径零改动（这是 AC3 的结构保证）。

### 2.3 权限矩阵与审计的新增项

| 命令 | student | admin | director |

| `waitlist join` | ✓（本人） | ✗ 3 | ✗ 3 |
| `waitlist list` | ✓ 仅本人（`--all` → 3） | ✓ 全部 | ✗ 3 |
| `waitlist cancel`（A） | ✓ 仅本人且 `waiting`，否则 1 | ✗ 3 | ✗ 3 |

审计（§7 表追加 1–2 行，`target_type` 枚举加 `waitlist`）：

| action | 触发点 | target_type / id | detail |

NFR-06 的"六类关键操作"**口径不变**；候补审计作为 CR 附加项，不计入 NFR-06 的 6 类，避免验收时对不上。

## 3 方案对比

人日口径：BA 600 / Dev 650 / QA 450 / PM 800 / CCB 500 元/人日（`08-cost.md` §1）。

| 方案 | 内容 | 人日拆解 | 人日 | 金额 | 关键路径 | 风险 |
|---|---|---|---|---|---|---|
| **A 完整** | 登记 + 管理员名单 + 取消登记 + 去重联动 | BA .25 / CCB .5 / Dev 1.5 / QA .75 / PM .25 | 3.25（区间 3.0–3.5） | **¥1,912.50** | **+1.5 天 → 20.25** | 超 20 天承诺 0.25 天；管理储备差 ¥12.5；取消功能带来"取消后又来占位"的状态口径讨论 |
| **B 最小** | 登记 + 名单（student 本人 / admin 全部）+ 应用层去重；无取消 | BA .25 / CCB .5 / Dev 1.0 / QA .5 / PM .25 | 2.5（区间 2.25–2.75） | **¥1,475** | **+1.0 天 → 19.75** | 学生登记错了无法自行撤回，只能找管理员（演示可接受）；20 天承诺余量仅 0.25 天 |
| **C 不实现/延后二期** | 维持基线，CR-01 结论记"不批准" | — | 0 | ¥0 | 0 → 18.75 | 客户演示后的唯一新诉求落空（R3）；候补继续走微信群 |

- A 的成本来源：Dev +0.5（取消子命令 + 去重联动）、QA +0.25（第 5 条用例 + 回归）。
- B 的工期影响即"Dev 串行 +1.0 天"；QA 0.5 天与 Dev 并行（QA 现有浮动 2.5–9.5 天），不占关键路径；CCB/BA 在 WP4 验收期间完成，不额外占链。
- C 的"节省"不是零成本：客户诉求未满足，验收时 S1 走查会缺一条演示项，且二次变更的评审费（¥250）迟早要花。

## 4 对基线的影响（以方案 B 为口径，A 的差异在括号内）

| 项 | 基线 v1.0 | 批准 CR-01 后 v2.0 | 说明 |
|---|---|---|---|
| 总人日 | 25.0 | 27.5（A：28.25） | +2.5 / +3.25 |
| 成本基线 BAC | 15,800 | **17,275（A：17,712.50）** | 变更整体并入新基线，`08-cost.md` §6 口径 |
| 应急储备 | 2,000 | 2,000（不动） | 仅 R1–R8 可用，变更不得挤占 |
| 批准预算（BAC+应急） | 17,800 | **19,275（A：19,712.50）** | A 超客户上限 19,700 达 ¥12.5 |
| 管理储备 | 1,900 | **425（A：−12.5）** | 1,900 − 1,475；A 已透支 |
| 关键路径 | 18.75 天 | **19.75 天（A：20.25）** | 20 天客户承诺的余量：0.25 / −0.25 |
| 里程碑 M4 / M5 | 17.25 / 18.25 | 18.25 / 19.25 | 整体后移 1.0 天，仍在 20 天内 |
| 是否需要 CCB 批准 | — | **是**（动管理储备 + 改范围基线 + 改架构契约 v1.1 + 进度/成本 v2.0） | 章程 §9.1 条件 3 |

**缓冲读数（重要）**：10.50 数据点已消耗缓冲 0.62 天（`stage3-log.md` §纠偏）。按此节奏，B 的实际完工预期约 19.75 + 0.62 ≈ **20.4 天**，已越过 20 天承诺；A 约 **20.9 天**，必破。故"批准 B"应附带止损条款：WP5（3.9）若再超期 ≥0.25 天，则砍 3.11 演示脚本的加演项、把 4.1/4.2 合并为一次 EVM 数据点，而不是顺延。

## 5 建议

**推荐方案 B。** 一句话理由：客户要的是"能看到谁在等"，B 用 2.5 人日 / ¥1,475 / +1.0 天把这件事做完，还能留在 20 天与 ¥19,700 两个硬约束之内；A 的取消功能只有演示价值，却同时顶破工期与客户上限。

**不做的后果**（对应 C）：①客户演示后提出的唯一新诉求被拒，`00-customer-brief.md` §6 记录的诉求无闭环，R3（需求理解偏差）在验收时转成实际扣分项；②候补仍走微信群，与本项目"减少人工协调"的目标相悖；③二期再提时仍要花同样的评审费与开发量，且届时没有 2.5 天缓冲，成本更高。
