# 多智能体团队结构（DeviceLoan MVP）

> 版本 v1.0 · 编制 PM · 2026-10-23 · 阶段：启动

本文回答三个问题：团队采用哪种组织结构、每个智能体负责什么并需要什么输入、智能体之间如何交互。角色职责的简表见 `02-charter.md` §6，干系人清单见 `03-stakeholders-kickoff.md`。

## 1 组织结构类型

本项目采用**项目型（Project-oriented）**结构。

| 结构 | 权力与资源 | 适用场景 | 本项目 |
|---|---|---|---|
| 职能型 | 项目经理权力最小，资源由职能经理分配 | 专业部门稳定、项目跨部门协调少 | 不采用 |
| 项目型 | 项目经理权力最大，团队专职服务单一项目 | 目标单一、工期紧、需要快速决策 | **采用** |
| 矩阵型 | 成员同时向职能经理和项目经理汇报 | 多项目共享专家资源 | 不采用强矩阵 |

选择理由：

- 20 个工作日、单一交付物，团队不需要在多个项目之间分摊；
- 团队只有 5 个角色，且“单人单角色”，再设职能经理层只会增加沟通成本；
- PM 需要对范围、进度、成本当场决策，项目型结构下授权最直接；
- QA 不向 Dev 汇报，独立出证据，形成一条**弱矩阵监督线**，避免开发者自证。

## 2 角色、输入与输出

| 角色 | 职责 | 主要输入 | 主要输出 | 决策边界 |
|---|---|---|---|---|
| PM | 派单、排期、成本与挣值核算、集成、对外汇报 | 客户需求档案、各角色交付物、EVM 数据、风险与变更 | 项目章程、WBS、进度与成本基线、状态报告、验收组织 | 可在基线内调整顺序与人力；偏差 >10% 上报发起人；动用管理储备须 CCB |
| BA | 需求与优先级、范围、架构与接口契约、WBS | 客户需求、变更请求、PM 任务单 | 商业论证、范围说明书、RTM、接口契约、WBS、变更影响分析 | 可提出需求优先级建议；不直接改代码，不代替客户确认 |
| Dev | 按契约实现工作包并自测 | 工作包说明、接口契约、QA 缺陷单 | 源代码、数据库脚本、演示数据、演示脚本、自测说明 | 可选择实现方案；不直接对接客户，不改验收标准 |
| QA | 独立验证、缺陷记录、验收证据 | 验收标准、接口契约、Dev 交付物 | 测试用例、缺陷清单、测试运行记录、QA 证据包、PASS/FAIL | 判定工作包是否通过；FAIL 即退回 Dev，不计 EV |
| CCB | 评审变更，裁定批准 / 拒绝 / 延期 | 变更请求、影响分析、PM/BA 评估意见 | 裁定结论、影响分析归档、收尾追认 | 变更裁决权；未批准不进入开发 |
| 客户 / 发起人（外部） | 提供需求与验收标准，签署章程与验收结论 | 项目周报、里程碑演示、变更影响 | 需求确认、验收结论、书面确认 | 验收与预算上限；不参与日常排期 |

## 3 交互关系

| 从 → 到 | 触发 | 传递内容 | 产物 |
|---|---|---|---|
| 客户 → PM / BA | 提出需求或变更 | 业务问题、验收标准、变更诉求 | 需求档案、变更请求 CR |
| PM → BA / Dev / QA | 阶段开始或工作包完成 | 任务单、优先级、截止时间 | 工作包说明、派单记录 |
| BA → Dev | 契约冻结 | 接口、数据模型、验收口径 | 接口契约 |
| Dev → QA | 工作包自测完成 | 代码、运行说明、自测结果 | 待验交付物 |
| QA → Dev | 测试失败 | 缺陷步骤、期望与实际 | 缺陷单 |
| QA → PM | 测试通过 | 证据包、覆盖率、结论 | QA 证据，计入 EV |
| PM / BA → CCB | 收到 CR | 影响分析（范围、进度、成本、NPV） | CCB 裁定 |
| PM → 客户 | 每周 / 每个里程碑 | 进度、成本、风险、演示 | 状态报告、验收记录 |

交互主线：

```text
客户/发起人
    │ 需求、验收
    ▼
   PM ──任务单──► BA ──接口契约──► Dev ──交付──► QA
    ▲               │                            │
    │               └──────────┐                 │ PASS/证据
    │ 偏差、风险                ▼                 ▼
    └──────────────────────  CCB  ◄── 变更请求 ──┘
                               │
                               └── 裁定：批准 / 拒绝 / 延期
```

## 4 运行规则

1. **任务单是唯一派单入口**：聊天里的临时要求不算任务，必须落到任务单或变更请求。
2. **契约先行**：BA 冻结接口契约后 Dev 才开工；开发中改契约按变更处理。
3. **证据驱动**：QA 出证据才计 EV；测试未通过的工作包不进入下一包。
4. **变更统一走 CCB**：CR → 影响分析（范围、进度、成本、NPV）→ 裁定 → 更新基线与台账；未批准不开发。
5. **升级规则**：进度或成本偏差超过 10%，PM 当天上报发起人；动用管理储备须 CCB 批准。
6. **人工签字**：章程、验收结论、财务参数确认由【待填】承担，不在智能体闭环内。

## 5 局限

- 单人单角色，无后备；角色不可用时由 PM 调整工作包顺序，不临时增编。
- 智能体之间以文档和任务单异步交互，不模拟实时会议；启动会以异步评审记录代替。
- 客户与发起人是人类角色，需求确认、书面确认和签字无法自动化。
